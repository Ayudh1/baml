title: (Experimental) Workflows
---

A [new experimental feature](https://www.boundaryml.com/blog/baml-workflows) allows
multiple LLM functions to be combined into a single high-level workflow. Workflows in
BAML, like LLM calls, are simply functions. They have parameters and return types,
and they can be compiled into functions in your host language to be called directly
from Python/TypeScript/Go etc.

## BAML Workflows

<Warning>
  This feature is experimental. The syntax and API are subejct to change,
  compiler errors may be less useful than those in the rest of the language,
  and the runtime behavior may not be correct. This feature is a technical
  preview intended to generate feedback for future refinement, and is not
  yet suitable for use in production apps.
</Warning>

Workflows differ from LLM functions in their function bodies, which look more similar
to the bodies of functions in general-purpose programming languages. For example, this
workflow takes a poem topic and returns two separate poems on the topic, one generated
by GPT4 and the other generated by Claude.

```baml BAML
// A normal BAML class.
class Poems {
    openai string
    claude string
}

// A Workflow, which can call other LLM functions or Workflows and
// compose their results.
fn TwoPoems(topic: string) -> Poems {
    let poem_length = 10;
    Poems {
        openai: CreateGPTPoem(topic, poem_length),
        claude: CreateClaudePoem(topic, poem_length)
    }
}

// The normal BAML functions we have always been able to write.
function CreateGPTPoem(subject: string, length: int) -> string {
  client GPT4o
  prompt #"
    Please write a {{ length }} line poem about the beauty of {{ subject }}.
  "#
}

// The normal BAML functions we have always been able to write.
function CreateClaudePoem(subject: string, length: int) -> string {
  client GPT4o
  prompt #"
    Please write a {{ length }} line poem about the beauty of {{ subject }}.
  "#
}

client<llm> GPT4o {
  provider openai
  retry_policy CustomRetry
  options {
    model gpt-4o
    api_key env.OPENAI_API_KEY
  }
} 

client<llm> Claude {
  provider anthropic
  options {
    model claude-3-haiku-20240307
    api_key env.ANTHROPIC_API_KEY
    max_tokens 1000

  }
}
```

### Learning the Workflow Syntax

Let's break down the components of a Workflow, and learn how to build up a
value using multiple LLM calls.

```baml BAML
fn TwoPoems(topic: string) -> Poems {
  ...
}
```

A Workflow looks a lot like a function from a normal programming language, it
begins with the keyword `fn`, followed by a custom name (`TwoPoems`), a list
of parameters, (in this example, just the parameter `topic`, which we specify
has type `string`), and then a return value `Poems`.

Inside the body, of the function, we can assign values to variables, and specify
the function's return value:

```baml BAML
fn TowPoems(topic: string) -> Poems {
  let poem_length = 10; // (A)
  Poems { // (B)
    openai: CreateGPTPoem(topic, poem_length), // (C)
    claude: CreateClaudePoem(topic, poem_length), // (D)
  }
}
```

 - (A): We assign the value `10` to the variable `poem_length`, so that we can
   share it in the two following function calls.
 - (B): The last item in the function's body is its return value. Here we are
   constructing a class `Poem`.
 - (C): The `Poem` class has two fields, `openai` and `claude`. On this line, we
   are specifying the value of the `openai` field as a call to the LLM function
   with two arguments: `CreateGPTPoem(topic, poem_length)`.
 - (D): We assign the `claude` field of the `Poems` class in the same way we
   specified `openai`, but calling a different function, `CreateClaudePoem`.

Another way to write this Workflow would be to assign the OpenAI and Claude
poems to variables, before using those values in the `Poems` constructor,
like this:

```baml BAML
function TwoPoems(topic: string) -> Poems {
  let poem_length = 10;
  let openai_poem = CreateGPTPoem(topic, poem_length);
  let claude_poem = CreateClaudePoem(topic, poem_length);
  Poems { openai: openai_poem, claude: claude_poem }
}

### Top-level definitions

You can bind values to variables at the top level of a BAML file, and then
share than value with several BAML functions later.

```baml BAML
let openai_example_poem = CreateGPTPoem("technology", 10);
let claude_example_poem = CreateClaudePoem("technology", 10);

fn TwoExamplePoems() -> Poems {
  Poems { openai: openai_example_poem, claude: claude_example_poem }
}
```

In this particular example, because the poems are defined as top-level values,
we can directly use them inside the body of `TwoExamplePoems()`. And because
they are top-level static values, we have lost the ability to dynamically
choose a topic (notice that the topic is hardcoded to "technology" in the 
calls to the LLM functions).

Top-level definitions may define some helper-values before specifying a final
static value. These helper values are only available in the scope of the
definition. For example:

```baml BAML
let example_poems = {
  let openai_poem = CreateGPTPoem("technology", 10); // (A)
  let claude_poem = CreateClaudePoem("technology", 10); // (B)
  Poems { openai: openai_poem, claude: claude_poem } // (C)
}
```

 - (A): The `openai_poem` variable will be available while computing `example_poems`,
   but other code in your BAML file can not access the `openai_poem` variable.
 - (B): Another helper variable.
 - (C): The final value of `example_poems` is a `Poems` instance that makes use
   of the two helper variables.

### Evaluation Order

You are probably used to a program running one line at a time, perhaps
with tools like `async` to allow concurrency. In BAML, although our
syntax resembles that of a synchronous function, you are actually building
a workflow. BAML will detect what parts of the function need to be evaluated
to compute the final result, and will attempt to evaluate LLM calls in
parallel if they are not dependent on one another.

The BAML VSCode Extension and [online playground](https://promptfiddle.com)
can help you understand the evaluation schedule of your functions. Just
write a test for your Workflow function, run it, and watch the various parts
of your function highlight as they are sent to the LLM provider.

This final example function has a susprising execution order because the
items in the returned list are in a different order than they are defined
in their helper variables.

```baml BAML
fn FourSeasons() -> string[] {
  let summer = CreateClaudePoem("summer", 10);
  let fall = CreateClaudePoem("fall", 10);
  let spring = CreateClaudePoem("spring", 10);
  let winter = CreateClaudePoem("winter", 10);
  [winter, spring, summer, fall]
}

test FourSeasons {
  functions [FourSeasons]
  args {}
}
```

<Note>
   Note that the seanons are listed in one order, and defined in another order.
   The order of evaluation follows the order of the items in the list, not the
   order that the items are defined.

   You may wonder why these items do not evaluate simultaneously, given that they
   have no mutual data dependencies. In the future, they will.
</Note>
